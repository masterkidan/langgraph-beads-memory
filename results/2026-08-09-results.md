# Demo results — 2026-08-09, qwen3:8b, N=3

Six runs (3 per condition), 0 errored turns, 42.2 minutes total. Raw transcripts
in `n3/`. Method, disclosed corrections, and limitations: [README.md](README.md).

**This is a designed demonstration, not a neutral benchmark.** The scenario was
built to exercise supersede-and-recall. These numbers show the mechanism works
on a case constructed for it — not that it wins in general.

## What holds up

**One metric separates cleanly: `uses_revised_budget`, 0/3 vs 3/3.** That is the
supersede-and-recall path the library exists for, and it is the result the design
predicts. Everything else is either tied or noisy.

**The failure it exposes is not amnesia.** In every baseline run the budget
update itself succeeded — the transcripts show "The budget has been successfully
updated to $50k per year", and the value is present in the LangMem store. Two of
three baseline runs then recommended **Weaviate at $60k/year against a $50k
budget**, justifying it on hybrid search and latency without mentioning cost.

So LangMem stored the constraint correctly. What failed is that retrieval was
something the agent had to *choose* to do, and at the moment of the decision it
didn't. Automatic injection puts the constraint in front of the model instead.
That is a narrower and more defensible claim than "better memory".

**Token cost, settled, and it reverses an earlier claim.** The treatment used
~45% *fewer* input tokens (10,083 vs 18,220), consistent across all three runs.
An earlier single run measured ~46% *more* and was published as an honest cost;
that run predated the delegation fix and is superseded. A compact,
relevance-ranked fact set is cheaper than accumulated history plus
memory-search payloads.

## What does not

**The baseline beat us on `buried_detail_recalled`, 3/3 vs 2/3.** I first
guessed this was architectural — that namespace isolation hid a sub-agent's
detail from the parent. **Checking the database disproved that.** In the one
treatment run that missed, the Qdrant quantization fact *was* present in the
root namespace with the `32` figure intact; the rollup worked exactly as
designed. The model simply answered "approximately 40%" — a hallucinated
number — with the correct fact available to it.

So this is a one-run difference at n=3 attributable to model variance, not to
the memory architecture. It is recorded here because it is the metric where we
lose, and because the first explanation offered for it was wrong.

**Three of six metrics are noisy in both conditions.** `mentions_selfhost`,
`mentions_primary_sources` and `buried_detail_recalled` flip between runs on
both sides. Only `uses_revised_budget` (and its consequence,
`mentions_feasible_option`) separates reliably.

**The judge is coarse.** It returned a flat 5/5/5 for the treatment in all three
pairs. The direction is credible — it was blinded, and the baseline transcripts
really do contain an over-budget recommendation — but a scale that never
discriminates within a condition is not measuring finely. Weight it as a
direction, not a score.

## Caveats

- **N=3 on one scenario with one model.** Enough to distinguish a reproducible
  pattern from a lucky run; not enough for a general claim.
- **qwen3:8b is unreliable at multi-tool root-level calling.** It emits
  malformed pseudo-tool-calls as plain text, and it repeatedly fought langmem's
  nested `content`/`id`/`action` schema ("It appears there is a persistent issue
  with the `content` field"). That is tool-schema ergonomics, not a memory
  failure, and it is a genuine difference in how hard the two libraries are for
  a small model to drive — but it is not the architecture under test.
- **Sub-agent execution is serialised** (`max_concurrency=1`). Concurrent
  requests reproducibly wedged Ollama; profiling showed the concurrency was
  worth only ~1.05x anyway on this hardware.
- **The scenario is tuned.** Two changes were made after seeing data (the
  buried-detail question wording, and delegation discipline in the prompt), both
  disclosed in [README.md](README.md) and inline in `demo/scenario.py`.

## Investigated: why `mentions_primary_sources` is only 1/3

Not a metric bug (checked: runs 0 and 2 mention it in no phrasing — not
"self-measured", "our own", "we measured"). Not a capture failure either: the
constraint is stored verbatim in the root namespace of every run.

It is a **retrieval-ranking failure, and the cause is fact granularity.** All
three of conversation 1's constraints arrive in one user message, and passive
capture stores that message as a *single* fact:

> "We need to pick a vector database for our product. Constraints: the budget is
> $100k per year, it must be self-hostable, and I only trust primary benchmark
> data we measured ourselves, not vendor marketing numbers."

One fact means one embedding, averaged across three unrelated topics — budget,
deployment model, evidence provenance. Reconstructing the conversation-3
retrieval against the real database confirms it never reaches the top-8:

```
run_treatment_0, top-8 for "which vector database should we pick and why?"
  1. [passive_capture] Given everything we've established, which vector database...
  2. [passive_capture] Please investigate our vector database options in depth...
  3. [passive_capture] Given the updated budget constraint of $50,000, Qdrant...
  4. [remember_tool  ] Based on the updated budget constraint of $50,000, Qdrant...
  5. [passive_capture] The in-depth investigations into pgvector, Qdrant, Weaviate...
  6. [passive_capture] The strongest runner-up to Qdrant...
  7. [passive_capture] The annual budget is now correctly noted as $50,000...
  8. [remember_tool  ] The annual budget for the vector database is $50,000...
  -> the conv-1 constraints fact does not appear
```

This explains **both** results at once. The budget survives (3/3) because it was
*restated* several times — as a correction, as conclusions, as summaries — so
multiple high-similarity facts carry it. The sourcing constraint was stated
*once*, early, bundled inside a longer sentence, and is crowded out by
conclusions that restate the budget.

So the mechanism does not preserve "constraints" in general. It preserves facts
that are **individually stated and repeatedly reinforced**. A constraint
mentioned once in passing degrades exactly as it would in an extraction store.

Candidate fixes, none implemented or measured yet:

- **Split multi-constraint messages into one fact per constraint**, so each gets
  its own embedding instead of an average across three topics. Most promising —
  it attacks the cause rather than the symptom.
- **Raise `k`** beyond 8. Cheapest, but pushes cost back up and only defers the
  problem as fact counts grow (run 0 had 38 active root facts).
- **Pin `user_input` constraint facts** so stated requirements are not evicted by
  the agent's own conclusions. Risks re-injecting stale constraints if the
  supersede path is not airtight.

Recording this as a known limitation rather than fixing it now: changing
retrieval after seeing which metric it costs us would invalidate this N=3 run,
and any fix needs its own measurement.

### A latent bug found while investigating this (fixed, does not affect N=3)

Probing whether the sliding window could be evicting the constraint surfaced a
separate defect. The retrieval query was taken from the *windowed* messages:

```python
query_text = next((m.content for m in reversed(windowed) if isinstance(m, HumanMessage)), None)
if query_text:
    facts = store.search(...)          # else: NOTHING injected
```

On a turn with enough tool calls to push the user's question past the window, no
`HumanMessage` remained in view, the query came back `None`, and **no facts were
injected at all** — memory silently switched itself off on exactly the long,
roundabout turns where it is most needed.

The window governs what the model re-reads; it must not govern what memory is
retrievable. The query now comes from the full message list, with a fallback to
the last non-empty message so a turn that opens with tool traffic still
retrieves.

**These N=3 results are unaffected.** The longest turn observed was exactly 10
messages against a window of 10 — the boundary was reached but not crossed, and
every conversation-3 turn was 2 messages. Verified per-turn across all six runs
before making the change.
